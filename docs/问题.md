# 已知问题与限制

## 怎么确认 STM32 在不在上传数据（PB5 状态灯）

不接电脑也能判断：板子上的 **PB5** 专门做这件事（PE5 是用户可控 LED，不参与状态指示，
否则语音/云端的开关灯会和状态指示打架）。代码在 `APP/status_led.c`，
调度里每 20ms 跑一次 `status_led_poll()`。

「闪」= 亮 120ms / 灭 120ms，一组闪烁之间 LED 是灭的。

| PB5 表现 | 含义 | 该查什么 |
| --- | --- | --- |
| **双闪**，每 2s 一组 | ESP32/MQTT 链路没通（初始化没跑完 **或** MQTT 掉线） | WiFi 是否可用、`APP/mqtt_config.h` 里的 SSID/密码是不是当前网络、ESP32 供电和串口接线、broker 地址端口；短暂双闪说明链路刚刚抖过，恢复后会自己回到单闪 |
| **三闪**，每 2s 一组 | 链路通了，但 **`home/cmd` 没订阅上** | 订阅被 broker 拒绝 / AT 固件不支持该主题；STM32 会每 60s 自动补订阅一次 |
| **一次长闪（500ms）**，每 2s | 订阅正常，但发布一直不成功（超 10s 没收到 `+MQTTPUB:OK`，或收到 `+MQTTPUB:FAIL`） | AT 通道是否卡在 `AT+MQTTPUBRAW` 的数据阶段、topic/长度是否被 ESP-AT 拒绝、broker 是否允许该 client id 发布 |
| **单闪**，每 3s 一次 | 正常：每成功发布一次闪一下（发布周期就是 3s） | 不用查，说明能上报、也能收到控制指令 |
| **全灭** | 链路刚建立、还没发出第一条；或者 MCU 卡死 | 先看串口有没有启动日志；一直全灭要查复位/供电 |

判断顺序建议：**先看灯**，再决定要不要接串口开 `ESP32_XIAOZHI_DEBUG`
（`APP/esp32_xiaozhi.c`，改成 1 后能在 USART1 看到完整 AT 交互）。

### 曾经踩过的坑：控制指令被静默吃掉

现象：`home/state` 每 3s 正常上报、MQTTX 里也能看到 `home/cmd`，但设备就是没反应。

原因：`process_status_lines()`（`APP/esp32_xiaozhi.c`）里漏了 `+MQTTSUBRECV:` 的 `break`。
状态行是"从缓冲开头一路消费到自己这里"的，所以循环越过订阅记录之后，记录后面那条空行
（或任意状态行）会把它连根吃掉，`handle_subrecv()` 根本没机会看到。

修法有两层：循环遇到 `+MQTTSUBRECV:` 立即 `break`；消费状态行前再夹一道
"绝不越过缓冲里第一条订阅记录"的保险。**改这个函数时不要删掉这两处。**

### 曾经踩过的坑：链路抖动被放大成一分多钟离线

现象：PB5 双闪，小智端看到 smart_home 反复掉线又上线，一次能断很久。

原因：`+MQTTDISCONNECTED` / `WIFI DISCONNECT` 一到就把初始化状态机整个拉回
`CWMODE` 重走一遍。问题是 ESP-AT 本身开着 MQTT auto-reconnect（`AT+MQTTCONN` 最后一位 `=1`），
几秒就能自己把连接接回来 —— 我们再插一脚重连，`AT+MQTTCONN` 会回 `ERROR`（已经连着），
重试 3 次（≈24s）→ `INIT_FAIL` → 冷却 30s → **`AT+RST` 把 ESP32 整个复位** →
WiFi 重新关联十几秒。一次几秒的抖动被放大成一分多钟。

现在改成分级处理：

| 事件 | 动作 |
| --- | --- |
| `WIFI DISCONNECT` / `+MQTTDISCONNECTED` | 只标记链路断开、停发上报，**不动**初始化状态机，交给 ESP-AT 自动重连 |
| `+MQTTCONNECTED` | 标记链路恢复，并把订阅标记清掉（订阅不会自动恢复，接着补订阅） |
| 链路断开超过 **90s** | 才升级：把状态机拉回 `CWMODE` 软恢复（不重启 ESP32） |
| 初始化连续失败 **3 轮** | 才 `AT+RST` 硬复位 |
| `AT+MQTTCONN` 之前 | 先 `AT+MQTTCLEAN=0` 清掉旧连接再连（ESP-AT **没有** `AT+MQTTDISCONNECT` 这条命令），避免"重复连接 → ERROR 0x6004 → INIT_FAIL → AT+RST" |
| `AT+MQTTCONN` 等待时长 | 16s。ESP-AT 自己等 MQTTCONN 的默认超时是 15s，我们必须等得比它久，否则它还在连我们就判超时重发，只会拿到 ERROR |

另外断链期间不再发 `AT+MQTTPUBRAW`（省掉每 3s 一条 ERROR），重连后立刻补发一条。

### 为什么小智端会显示「桥在线，无设备」

`home/state` 是 **retained** 主题。小智一连上 broker，broker 就会把**上一次**留下的那条
推给它，所以：

- 即使 STM32 早就断了，小智端仍然会显示"桥在线"——那是历史数据，不是实时状态；
- MQTTX 同理：新订阅的一瞬间会收到 retained 那条，之后才是实时流量。

所以**判断 STM32 到底有没有在传，不能只看小智端的显示**，要看 PB5 状态灯，
或者在 MQTTX 里对 `home/state` 观察是否每 3s 有新的一条。

如果确认 STM32 侧没在传，而 broker 上又留着一条旧的 retained `home/state`，
可以用下面这条命令清掉它，避免误导：

```bash
mosquitto_pub -h <broker> -p <port> -u <user> -P <pass> -t home/state -r -n
```

（`-r` 加空 payload 就是"清除该主题的 retained 消息"。）

## 风扇无法完全停转

当前风扇模块为 `G / V / S` 三线接口。如果只接 `G + V` 就会满速转动，说明供电后模块默认开启，`S` 脚可能只负责调速或使能，未必能切断风扇供电。

影响：

- PWM 可以改变转速，但可能无法让风扇完全归零。
- 若需要可靠停转，应增加电源开关管、EN 控制或更换支持关断的风扇模块。
- 当前风扇使用 TIM4_CH4 / PD15，TIM4 同时服务 WS2812，频率并非专为普通风扇 PWM 设计。

## 硬件设计问题

- 当前硬件设计周期较短，需要特别注意电源稳定性和模块共地问题。
- PCB 没有预留足够扩展接口，后续通过飞线补接时更容易出现接触不良、电源压降和干扰问题。
- PM2.5 粉尘传感器线束较细且引脚较多，当前更适合焊接固定；拆装和返修时容易引入连接问题。

## ESP32 初始化和 AT 指令超时

ESP32 使用 AT 指令连接 WiFi 和 MQTT。初始化过程中可能出现超时或 busy 状态，需要等待非阻塞初始化状态机重试。

影响：

- WiFi 信号、MQTT broker 可用性、AT 固件版本和供电稳定性都会影响初始化成功率。
- `APP/esp32.c` 中仍保留阻塞式初始化接口，但当前调度中主要使用非阻塞初始化。
- 换成 OneNET 后端（`ESP32_MQTT_BACKEND_XIAOZHI = 0`）后必须同步产品 ID、设备名、token、属性名和数据类型。
- WiFi 掉线和 broker 掉线都会让状态机回到 `CWMODE` 重走 `CWJAP → MQTTCONN → MQTTSUB`：
  订阅不会由 ESP-AT 自己恢复，不重走一遍就会"能发不能收"（`home/cmd` 静默失效）。

## OneNET 属性名与类型

当前代码上传 `MQ2` 和 `PM25` 的 ADC 原始值，类型应按整数配置，范围建议 `0~4095`，步长 `1`。

需要注意：

- 代码中 RGB 红色属性名使用 `RGB1_RAD` / `RGB2_RAD`，如果云端模型使用 `RED`，需要统一修改。
- 云端数据类型和步长不一致时，上传可能失败或显示异常。

## 烟雾 DO 连接需按当前硬件确认

当前烟雾模拟量 AO 已按实际接线配置为 PA1 / ADC1_IN1，`APP/smoke.c` 中 `SMOKE_ADC_CHANNEL` 为 `ADC_CHANNEL_1`。代码还保留 PC2 作为烟雾 DO 低电平报警辅助输入。

影响：

- 如果硬件没有实际接烟雾 DO，应主要使用 PA1 ADC 原始值判断烟雾状态。
- PA2 当前是 USART2_TX，用于 ESP32 通信，不应再接烟雾 DO。
- 后续硬件修版可继续保留 PC2 作为 DO，或完全移除数字报警脚依赖。

## ASRPRO 需要单独烧录

`asrpro_code.cpp` 不参与 STM32 CMake 编译，需要在 ASRPRO / 天问 Block 环境中单独更新。

当前语音逻辑限制：

- 唤醒词后保留 30 秒命令等待窗口。
- 查询命令保留 30 秒窗口，避免查询结果被退出提示打断。
- 控制命令执行后不主动开启等待窗口，避免执行一次命令后马上播报退出提示。
- 人脸和报警的外部 `PLAY/PLAYS` 不主动打开唤醒窗口。

如果烧录后仍出现无人唤醒时播报退出提示，需要检查 ASRPRO 是否误唤醒，或是否存在旧代码未覆盖。

## OpenART 人脸识别限制

`openart.py` 当前只识别 `zeng` 一个对象。

限制：

- 没有多用户身份管理。
- 没有陌生人告警逻辑。
- 识别准确率依赖模型、光照、摄像头角度和 SD 卡中模型文件路径。
- STM32 侧只处理 `FACE:ZENG,score`、`FACE:NONE`、`FACE:ERR,...`。

## 调试日志默认关闭

UART1 是下载和调试接口。为了避免串口占用和运行干扰，模块日志默认关闭。

需要调试时，在对应模块中开启 `*_DEBUG` 宏；测试完成后应恢复为 `0`。

## 传感器数据为 ADC 原始值

烟雾和 PM2.5 当前不再换算为 ppm 或 ug/m3，而是使用 ADC 原始值。

原因：当前模块换算后正常值基本接近 0，不利于调试阈值和观察变化。

影响：

- 显示、语音和 OneNET 数据更直观，便于根据实际模块调阈值。
- 阈值需要根据实际环境、供电、传感器预热状态重新标定。

### 当前阈值与告警方式

| 项目 | 值 | 定义位置 |
| --- | --- | --- |
| 烟雾触发阈值 | ADC `800` | `APP/smoke.h` 的 `SMOKE_ALARM_ADC_THRESHOLD` |
| 烟雾恢复阈值 | ADC `650` | `APP/smoke.h` 的 `SMOKE_ALARM_ADC_CLEAR` |
| 粉尘触发阈值 | ADC `800` | `APP/voice.c` 的 `VOICE_PM25_ALARM_ADC` |
| 粉尘恢复阈值 | ADC `650` | `APP/voice.c` 的 `VOICE_PM25_CLEAR_ADC` |

（原值：烟雾 `300`、粉尘触发 `420` / 恢复 `355`。原阈值落在 MQ-2 干净空气的
读数范围内，环境稍差就会持续告警，所以整体上调。以上仍只是测试版本默认值，
换环境、换供电、换模块后都要重新标定。）

**告警是边沿触发，不是周期性重复播报**：

- 读数越限 → 播报一次，进入"已播报"状态；
- 读数回到恢复阈值以下 → 认为环境恢复，重新武装；
- 只有"恢复过、再越限"才会再播报一次。

也就是说环境一直差只会念一次，不会每 10s 念一遍。恢复阈值低于触发阈值，
中间那段是回差带，避免读数在阈值附近抖动时反复播报。

**如何标定**：把 `APP/voice.c` 里的 `VOICE_ALARM_DEBUG` 改成 `1`，用串口助手看
USART1 上每秒一条的 `[ALARM]` 日志（含两个通道的读数、阈值、锁存状态），
干净环境下取稳定读数再加上一截余量作为触发阈值，恢复阈值取触发值往下 15%~20%。
定标完把 `VOICE_ALARM_DEBUG` 改回 `0`。
