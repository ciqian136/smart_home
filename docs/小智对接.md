# 小智（xiaozhi-esp32）对接远程智能家居

本文是 `smart_home_final`（STM32F103 智能家居）与 `xiaozhi-esp32-main`（小智 ESP32-S3 固件）
之间对接的**唯一契约文档**。两端代码里的常量、字段名、主题名必须和本文一致；改一端就要改另一端。

---

## 1. 目标与结果

目标：用户对着小智说话，小智通过语音识别 → 云端大模型 → MCP 工具调用，控制**远程**的
STM32 智能家居（客厅灯带 1/2、风扇、板载 LED），并能实时读到家里的温湿度、光照、PM2.5、烟雾。

结果链路：

```
       说话
用户 ────────► 小智 ESP32-S3 ──(MCP tool call)──► DashboardModel
                                                     │ publish
                                                     ▼
                                     MQTT broker  home/cmd
                                                     │
                                                     ▼
                                   ESP32 AT 固件 ──► STM32F103
                                                     │ 执行
                                       灯带1/2 · 风扇 · LED
                                                     │ publish
                                                     ▼
                                     MQTT broker  home/state
                                                     │
            小智订阅 → 解析 → 仪表盘/工具返回 ◄───────┘
```

"远程"的含义：两端**不在同一条串口/同一块板子上**，只共享一个公网 MQTT broker
（`eb1hd28697538.vicp.fun:37061`，内网穿透出来的），所以指令必须走 MQTT 主题。

## 4. MQTT 契约

### 4.1 连接参数

| 项 | 值 | 定义位置 |
| --- | --- | --- |
| broker | `mqtt://eb1hd28697538.vicp.fun:37061` | STM32 `mqtt_config.h` / 小智 `secrets.h` |
| 用户名 | `mqttuser` | 同上 |
| 密码 | `0e0098b995305cd4` | 同上 |
| STM32 client id | `smart_home_stm32`（`AT+MQTTUSERCFG` 的 client_id 参数） | `mqtt_config.h` |
| 小智 client id | `esp_mqtt_client` 默认值（基于 MAC） | ESP-IDF 默认 |

> 两端 client id 必须不同，否则 broker 会把先连上的那一个踢掉。
>
> **凭据不要外发。** 真实密码只应出现在 `APP/mqtt_config.h`（模板 `mqtt_config.h.example`）
> 和 `xiaozhi-esp32-main` 的 `secrets.h`（模板 `secrets.h.example`）里。本文档为了能直接
> 复制命令带了明文示例，**对外分发前请先把这几处密码替换掉**。

### 4.2 主题

| 主题 | 方向 | 是否 retain | QoS | 说明 |
| --- | --- | --- | --- | --- |
| `home/state` | STM32 → 小智 | **是** | 0 | 设备状态信封，周期 3s，控制生效后立刻补发一条；retain 让新上线的订阅者立刻拿到最后一份状态 |
| `home/cmd` | 小智 → STM32 | 否 | 0 | 语音控制指令 |

`home/state` 用 retain（STM32 侧 `AT+MQTTPUBRAW=0,"home/state",<len>,0,1` 最后一个参数）：
小智的 MQTT 是**按需连接**的，连上瞬间 broker 就会把最后一份状态推过来，仪表盘不会空白。

代价是：**STM32 断了之后小智端仍会显示最后一次的状态**（"桥在线"），那是历史数据不是实时状态。
所以"STM32 到底有没有在传"不能只看小智端 —— 用 §9.4 的 PB5 状态灯判断。

`home/cmd` **刻意不用 retain**：它是一次性动作，retain 会让 STM32 每次重连都把最后一条指令
重放一遍（"上次说开灯"变成"每次重连都开灯"）。

## 5. `home/state` 上行格式（既有，未改动）

```json
{
  "source": "smarthome-bridge",
  "version": "1.0.0",
  "ts": 1789818624,
  "count": 1,
  "online": true,
  "devices": {
    "smart_home_01": {
      "name": "living_room",
      "online": true,
      "temp": 25.5,
      "humi": 60.0,
      "light": 123.4,
      "pm25": 418,
      "mq2": 315,
      "fan": 500,
      "led": false,
      "rgb1": [255, 200, 100],
      "rgb2": [0, 0, 0]
    }
  }
}
```

- `ts` 来自 `AT+CIPSNTPTIME?`（东八区换算成 UTC 秒）。
- `temp/humi/light` 只在该传感器就绪时才出现；`pm25/mq2` 是 ADC 原始值 `0~4095`。
- `rgb1/rgb2` 是 `[r,g,b]`，`0~255`；全 0 表示该灯带关闭。
- 小智侧解析器同时接受 `[r,g,b]` 数组和 `{"r":..,"g":..,"b":..}` 对象。

## 6. `home/cmd` 下行格式（本次新增）

### 6.1 控制指令

```json
{
  "id": "sh-7",
  "source": "xiaozhi",
  "device": "smart_home_01",
  "params": {
    "led": true,
    "fan": 500,
    "rgb1_r": 255,
    "rgb1_g": 200,
    "rgb1_b": 100
  }
}
```

`params` 里**所有字段都是可选的，只应用出现的字段**；没出现的保持设备当前值。
`rgb*` 三个通道也可以只给一个（例如只发 `"rgb1_r":255`），另外两个沿用当前值。

| 字段 | 类型 | 范围 | 作用 |
| --- | --- | --- | --- |
| `led` | bool | `true` / `false`（也接受 `1` / `0`） | 板载指示灯开关 |
| `fan` | int | `0~1000`（`0`=停） | 风扇转速，超出钳位 |
| `rgb1_r` `rgb1_g` `rgb1_b` | int | `0~255` | 灯带 1（48 灯，`APP/ws2812.c`） |
| `rgb2_r` `rgb2_g` `rgb2_b` | int | `0~255` | 灯带 2（192 灯，`APP/ws2812_2.c`） |

> 布尔既接受 `true`/`false` 也接受 `1`/`0`（写成字符串 `"1"` 也认）。
> 旧版 `parse_bool_value()` 只认 true/false，于是 OneNET 习惯的 `"led":1` 会被解析成
> **0** —— "云端让开灯、设备反而关灯"。现在 `APP/json_parser.c` 一并接受这些写法，
> `json_find_value()` 也容忍 `"key": {"value": X` 这种带空格的包装。
>
> 负载最外层必须是 JSON 对象（`{`）。STM32 侧以此作为"排版认对了"的最后一道校验，
> 避免误判的 `+MQTTSUBRECV` 排版把垃圾喂进解析器。

兼容写法（老 OneNET 命名，STM32 侧同样识别，方便旧脚本直接复用）：
`LED`(bool)、`RGB1_RAD` / `RGB1_GREEN` / `RGB1_BLUE`、`RGB2_RAD` / `RGB2_GREEN` / `RGB2_BLUE`（int）。
另外 `{"key":{"value":X}}` 的包装形式也接受（`parse_onenet_params` 同时支持两种）。

### 6.2 查询指令

```json
{"id": "sh-8", "source": "xiaozhi", "device": "smart_home_01", "op": "query"}
```

STM32 收到后**不等发布周期**，立刻重发一次 `home/state`。

### 6.3 回执方式

没有单独的回执主题。控制生效后 STM32 立刻重发 `home/state`，那一条既是回执也是新状态：

- 小智侧：`self.home.*` 工具返回时带的是**上一次**上报的状态，并附 `hint` 说明新状态马上到；
  需要确认时再调 `self.home.get_status`。
- 仪表盘最近消息条里可以直接看到 `home/cmd` 和紧跟着的 `home/state`。

## 7. STM32 侧实现说明

### 7.1 初始化状态机新增一步

`APP/esp32_xiaozhi.c` 的 `esp32_xiaozhi_init_nonblock()`：

```
... ATE0 → AT+RST → AT+CWMODE=1 → AT+CWJAP → AT+MQTTUSERCFG → AT+MQTTCONN
    → 【新增】AT+MQTTSUB=0,"home/cmd",0        (SUB_CMD / SUB_CMD_WAIT)
    → AT+CIPSNTPCFG → DONE
```

- 订阅失败**不让整个初始化失败**：状态上报是主链路，订阅是附加能力。
  重试 3 次后继续走 NTP，等补订阅把它捡回来（见下一条）。
- **订阅补漏**：`esp32_xiaozhi_check_online()` 里每 60s 检查一次，`sub_ok == 0` 就把状态机
  拉回 `SUB_CMD` 重试。ESP-AT 自己的 MQTT 重连不会恢复订阅，没有这一步就会出现
  "能上报、控制没反应"，只能等重启。订阅失败时 `AT+MQTTSUB` 回 `ERROR` 立刻算一次失败，
  不干等满 5s —— 否则补订阅本身会把状态上报拖住。
### 7.1.1 断线恢复：分级处理，不要一抖就重走初始化

**这是踩过的坑**：最初 `+MQTTDISCONNECTED` / `WIFI DISCONNECT` 一到就把状态机整个拉回
`CWMODE` 重走一遍。但 ESP-AT 本身开着 MQTT auto-reconnect，几秒就能自己接回来；
我们再插一脚，`AT+MQTTCONN` 会回 `ERROR`（已经连着）→ 重试 3 次（≈24s）→ `INIT_FAIL`
→ 冷却 30s → **`AT+RST` 复位 ESP32** → WiFi 重新关联十几秒。
一次几秒的抖动被放大成一分多钟离线，表现出来就是"反复掉线、很久才回来"（PB5 双闪）。

现在的分级策略：

| 事件 | 动作 |
| --- | --- |
| `WIFI DISCONNECT` / `+MQTTDISCONNECTED` | 只把 `mqtt_up`/`sub_ok` 清零、停发上报；**不动**初始化状态机，交给 ESP-AT 自动重连 |
| `+MQTTCONNECTED` | 标记链路恢复，并把 `sub_ok` 清零（订阅不会自动恢复，接着补订阅） |
| `mqtt_up == 0` 持续 **90s** | 判定自动重连救不回来，才把状态机拉回 `CWMODE` 软恢复 |
| 初始化连续失败 **3 轮** | 才 `AT+RST` 硬复位（怀疑 ESP32 自己卡住） |
| 每次 `AT+MQTTCONN` 之前 | 先 `AT+MQTTCLEAN=0` 清掉旧连接再连，避免"重复连接 → ERROR 0x6004 → INIT_FAIL → AT+RST"（ESP-AT **没有** `AT+MQTTDISCONNECT` 命令，正确的是 `AT+MQTTCLEAN=<LinkID>`） |
| `AT+MQTTCONN` 等待时长 | 16s —— ESP-AT 自己等 MQTTCONN 的默认超时是 15s（命令里的 `<timeout_ms>` 默认 15000），我们必须等得比它久，否则它还在连我们就判超时重发，只会拿到 ERROR |

断链期间 `esp32_run_send` 直接跳过（不再每 3s 白挨一条 ERROR），重连后因为
`publish_now` 还在，会立刻补发一条状态。

> 相关状态：`mqtt_up`（MQTT 连接）、`sub_ok`（`home/cmd` 订阅）、`link_down_tick`（掉线起点）、
> `fail_cycles`（连续失败轮数）。`mqtt_up` 由 `AT+MQTTCONN` 成功、`+MQTTCONNECTED` 置位，
> 由 `+MQTTDISCONNECTED`、`WIFI DISCONNECT`、`AT+MQTTDISCONNECT` 清零。
> PB5 状态灯判断"双闪"用的是 `esp32_xiaozhi_link_ok()` = `esp32_initialized && mqtt_up`，
> **不能**只看 `esp32_initialized`（broker 掉线时状态机仍是 `DONE`）。

### 7.2 `+MQTTSUBRECV` 解析

**官方（ESP-AT 文档）确认的格式是排版 A**：

```
+MQTTSUBRECV:<LinkID>,<"topic">,<data_length>,<data>
```

历史上工程里两处旧代码各按一种排版写过：

```
A: +MQTTSUBRECV:<link>,<topic>,<data_len>,<data>   （ESP-AT 官方文档，实际就是这种）
B: +MQTTSUBRECV:<link>,<data_len>,<topic>,<data>   （json_parser.c 旧注释里那种，实际不存在）
```

共同点是**负载都在第 3 个逗号之后**，差别只在"长度和主题谁在前"。
所以 `handle_subrecv()` 不写死顺序：把第 1、2 个字段都试成十进制数，是数字的那个当长度，
另一个当主题。两种固件都能正确取到边界，负载里出现逗号/引号/花括号也不会解析错。

防御措施：
- 长度字段认不出来 / 分隔符不够 / `data_len` 超过接收缓冲 → 退化成"吃掉到本行行尾"，
  宁可丢一条也不卡死接收缓冲。
- 缓冲顶满还是收不齐 → `esp32_rx_clear()` 并**同步局部长度**，避免函数末尾把陈旧长度写回全局。
- 无论主题是否匹配都会消费掉整条记录，只有 `home/cmd` 且负载以 `{` 开头才执行。

> **改 `process_status_lines()` 时最容易踩的坑**：状态行是从缓冲开头一路消费到自己那里的，
> 一旦循环越过了 `+MQTTSUBRECV` 记录，记录后面那条空行（或任意状态行）就会把整条订阅
> 记录连根吃掉，`handle_subrecv()` 再也看不到它。
> 现象极具迷惑性：**`home/state` 一切正常，但小智怎么都控制不了设备，MQTTX 里也看不到
> STM32 有任何反应**（因为它压根没收到）。
> 所以那里有两道保险：遇到 `+MQTTSUBRECV:` 立即 `break`；消费任何状态行之前再夹一道
> "绝不越过缓冲里第一条订阅记录"的判断。删掉任何一道都会复发。

AT 命令的确切名字和应答都以官方文档为准
（[MQTT AT Commands](https://docs.espressif.com/projects/esp-at/en/latest/esp32/AT_Command_Set/MQTT_AT_Commands.html)）。
几个容易写错的：

| 用途 | 正确命令 | 备注 |
| --- | --- | --- |
| 关闭 MQTT 连接 | `AT+MQTTCLEAN=<LinkID>` | **没有** `AT+MQTTDISCONNECT` 这个命令；官方 MQTTCONN 文档明确说重连前要先 MQTTCLEAN、重新配置参数 |
| 重复连接已连着的 broker | —— | 回 `ERROR` + `ERR CODE:0x6004`（`AT_MQTT_ALREADY_CONNECTED`） |
| 订阅已订阅过的主题 | —— | 回 `ALREADY SUBSCRIBE` 再 `OK`，所以补订阅是幂等的 |
| `AT+MQTTPUBRAW` 的应答 | `OK` 然后是 `>`，之后 `+MQTTPUB:OK` / `+MQTTPUB:FAIL` | 数据必须严格按 `<length>` 个字节发完 |

### 7.3 上报链路（`AT+MQTTPUBRAW`）的三个坑

`home/state` 走 `AT+MQTTPUBRAW=0,"home/state",<len>,0,1`：先发命令、等 `>`、再发原始 JSON。
这条路有三个必须处理的时序问题，改动时别踩回去：

1. **`OK` 和 `>` 是两条应答，可能分两次收上来。** 只看到 `OK` 就把 `at_cmd_busy` 放掉、
   并把 `raw_wait_prompt` 清掉，后面的 `>` 就成了孤儿，ESP-AT 会一直停在"等 length 个字节"
   的数据阶段，把后续 AT 指令当负载吃掉（然后往 `home/state` 发一条垃圾）。
   → 代码里 `process_status_lines` 的 `OK` 分支在 `raw_wait_prompt` 为真时不收尾。
2. **通用 AT 超时（5s）不能插手这条命令。** 同理，超时收尾会在数据阶段中途撒手。
   → `esp32_xiaozhi_at_busy_guard()` 给它单独计时（10s，ESP-AT 文档允许 MQTT 命令最多 10s）。
   真等不到 `>` 时，**主动把 length 个字节补齐**，让 ESP-AT 走完这次发布、恢复 AT 通道同步；
   这次发上去的内容会是垃圾，但下一条周期上报（≤3s）会覆盖掉 —— 比链路错位几十秒划算。
3. **`>` 只在下一条订阅记录之前找。** 在整个接收缓冲里 `strchr('>')` 会被后面某条订阅
   消息负载里的 `>` 骗到，把记录头截断掉；但边界也不能用"第一个换行"——提示符自己
   可能带 `\r\n` 收尾，那样会连它一起被当成空行吃掉。
4. **迟到的回执不能收尾"新的一次发布"。** 超时补发之后 ESP-AT 还会为那次发布补一条
   `+MQTTPUB:OK`；如果它落在下一次发布的等 `>` 期间，无条件收尾会把新那次发布的提示符
   变成孤儿。所以 `+MQTTPUB:OK/FAIL` 只在 `raw_active && !raw_wait_prompt` 时才收尾。
5. **负载写不进 TX 环时不能撒手。** `my_uart_write` 是全有或全无；没进去说明 ESP-AT
   还差 `length` 个字节，这时清掉占位会让后续 AT 指令被当成负载。代码里退避重试若干次，
   仍失败就恢复等待状态交给超时路径。

另外：
- `+MQTTDISCONNECTED` 不会去动"正在飞"的命令状态：`at_cmd_busy` 交给通用超时处理，
  等 `>` 的负载也不清（ESP-AT 可能还在数据阶段）。
- `handle_ntp_line()` 在等 `>` 期间也不清 `at_cmd_busy`，否则 `esp32_run_send` 会在
  ESP-AT 的数据阶段里再发一条 `AT+MQTTPUBRAW`。
- `esp32_xiaozhi_run_send()` 额外用 `raw_active` 挡一次：上一次发布的负载刚写完、
  还在等 `+MQTTPUB:OK` 时，不允许再开一次发布。

### 7.4 指令执行

`APP/home_cmd.c`：

- 用 `parse_onenet_params()` 两轮解析：标准命名一轮 + OneNET 旧命名一轮，最后按位合并。
- 全部数值钳位（RGB `0~255`、风扇 `0~1000`）。
- 返回 `HOME_CMD_NONE` / `HOME_CMD_APPLIED` / `HOME_CMD_QUERY`；
  非 `NONE` 时 `esp32_xiaozhi_publish_now()` 置位，下一轮 `esp32_run_send` 跳过 3s 周期立刻上报。

### 7.5 线程/调度

- `esp32_run_recv()` 在 `schedule_run()` 主循环里每圈调用 → 指令处理是**同步**的，不占用中断。
- `esp32_run_send` 是 100ms 定时任务，实际发布间隔由 `SMART_HOME_MQTT_PUBLISH_INTERVAL_MS`（3s）控制。
- 发布走 `AT+MQTTPUBRAW`：先发命令等 `>`，再发原始 JSON（避免 `AT+MQTTPUB` 的转义地狱）。

## 8. 小智侧实现说明

### 8.1 MCP 工具表

注册位置：`esp32s3-co5300-460.cc` 的 `InitializeTools()` → `RegisterHomeMcpTools()`。

| 工具 | 参数 | 说明 |
| --- | --- | --- |
| `self.home.get_status` | 无 | 全部设备读数 + 链路状态；只读，不主动拉起链路 |
| `self.home.set_light` | `strip`("1"/"2"/"both")、`on`、`color`、`r`、`g`、`b` | 灯带开关与颜色 |
| `self.home.set_fan` | `on`、`gear`(1~4)、`speed`(0~1000) | 风扇开关与转速 |
| `self.home.set_led` | `on` | 板载指示灯 |
| `self.home.refresh` | 无 | 发 `op=query`，让家里立刻上报一次（只要求自己的 MQTT 链路通） |

颜色名支持中英文：`red green blue white warm warm-white cool purple cyan yellow orange pink off`，
以及 `红 绿 蓝 白 暖白 冷白 紫 青 黄 橙 粉 关 关灯 灭` 等中文写法
（用户说的是中文，模型很可能直接把"蓝色"塞进 `color` 参数；只认英文会在发布之前就报错返回）。
只说"开灯"不给颜色时，沿用该灯带上一次的颜色；家里还没上报过就退回暖白 `(255,180,107)`。
`strip="both"` 时两路各自取自己的上次颜色，不会把灯带 1 的颜色串到灯带 2。

**控制类工具的两个前置检查**（缺一不可）：

1. 自己的 MQTT 链路通不通（`link`）。
2. **家里最近有没有上报** —— 本机收到 `home/state` 的时刻超过 15s 就当成掉线，
   返回 `ok:false, reason:"home_offline"`，并让模型告诉用户"设备像是离线了"。
   只查第 1 条会出现"链路好好的、设备已经断电"时还回答用户"已经帮您打开了"。
   （判断只认本机接收时刻：`home_ts` 是桥自己的时钟，而且 retained 消息会让它一直显得很新。）

`self.get_device_status` 会额外带一段 `smart_home` 摘要（`linked` / `reported` / `online` /
`stale` / `device_count` / 首个设备的 `temp humi light fan led rgb1 rgb2`），
所以模型查状态不必额外调工具。

### 8.2 MQTT 链路常驻（关键改动）

原来的生命周期是"进需要数据的页面才 `Start()`、离开就 `Stop()`"。
但智能家居工具是在**对话**里调的，那时界面停在原生语音 UI，仪表盘页面早就关了 ——
照原样就会"链路已断开，工具发不出指令"。三处改动：

1. `DashboardModel::SetPinned(true)`：`RegisterHomeMcpTools()` 里调用；置位后 `Stop()` 只打日志不断链。
2. `esp32s3-co5300-460.cc` 覆写 `SetNetworkEventCallback()`：收到 `NetworkEvent::Connected`
   就 `DashboardModel::Instance().Start()`（幂等），并把事件转发给基类回调（Application 用它更新状态栏图标）。
3. 工具内部再兜一次：`LinkSnapshot()` 先 `Start()`，没连上就返回可重试的 `ok:false + hint`。

并发：`Start()/Stop()/PublishCommand()` 用独立的 `lifecycle_mutex_` 串起来，
保证发布时客户端不会被并发 `Stop()` 销毁；它和事件回调用的 `mutex_` 不嵌套，不会死锁。

### 8.3 关于 `xiaozhi-esp32-main/esp32/`

`esp32/` 是本板**旧的独立仪表盘工程**（自带 `mqtt_mini.c`、`platformio.ini`），
`main/`（小智固件，`main/boards/custom/esp32s3-co5300-460/`）才是现在跑小智 AI 的那一份。
本次对接改的是 `main/`，`esp32/` 保持原样（它本来就能订阅 `#` 看到 `home/state` 和 `home/cmd`，可当调试用）。

### 9.4 不接串口怎么判断 STM32 在不在传：PB5 状态灯

板子上三颗 LED：一颗电源指示，PE5 是用户可控的板载 LED，**PB5 是上传状态灯**
（`APP/status_led.c`）。灯语：

| PB5 | 含义 |
| --- | --- |
| 双闪，每 2s 一组 | ESP32/MQTT 还没连上 —— 查 WiFi、`mqtt_config.h` 的 SSID/密码、ESP32 供电与接线 |
| 三闪，每 2s 一组 | 连上了，但 `home/cmd` **没订阅上** —— 控制指令收不到，小智"点不动" |
| 一次长闪（500ms），每 2s | 订阅正常但发布一直不成功（超 10s 没有 `+MQTTPUB:OK`，或收到 `+MQTTPUB:FAIL`）—— 查 AT 通道 / topic / broker |
| 单闪，每 3s 一次 | 一切正常：发得出去、也收得到控制指令 |
| 全灭 | 链路刚建立还没发过，或者 MCU 卡死 |

**"小智端显示桥在线、但 MQTTX 收不到新数据"时先看这颗灯**：它是唯一不受 retained
消息误导的现场证据。详细排查步骤见 `问题.md` 的「怎么确认 STM32 在不在上传数据」。

## 10. 已知限制

1. **指令不重发**：`home/cmd` 是 QoS 0 且不 retain。STM32 离线期间发的指令会丢失，
   重连后不会补发。需要可靠投递就得引入应用层序号 + 重发，当前未做。
2. **一个设备 ID**：`count` 固定为 1，设备 ID 由 `SMART_HOME_MQTT_DEVICE_ID` 决定。
   协议本身支持 `devices` 里多台，两端解析器都是循环/取首台，扩多台不需要改协议。
3. **`+MQTTSUBRECV` 长度字段限制**：字段必须是纯十进制（1~5 位）。主题里含逗号会打乱
   逗号分段，当前只订阅 `home/cmd`，不受影响。
4. **工具返回的是旧状态**：MQTT 是异步的，`self.home.*` 返回体里的 `devices` 是上一次上报，
   已用 `hint` 明确告知模型。要实时值请先 `self.home.refresh`。
5. **MQTT 常驻占用内存**：pin 之后离开仪表盘页面不再释放 `esp_mqtt_client`（约数 KB）。
   这是"对话中随时能控制"的必要代价；如需回收，把 `SetPinned(false)` 并在工具里现拉链路即可
   （第一次指令会因链路未就绪而需要重试一次）。
6. **未做触摸屏控制**：「智能家居」页目前仍是只读展示。加触摸按钮只需在
   `dashboard_view.cc` 的 `BuildServicePage(page, 3, ...)` 上挂按钮，回调里调
   `DashboardModel::Instance().PublishCommand(...)`；留作后续。
7. **订阅丢失的兜底**：`AT+MQTTSUB` 连续失败 3 次会带着"没订阅"继续走完初始化
   （状态上报是主链路，不能因为订阅失败整体失败）。之后由 `check_online()` 每 60s
   把状态机拉回 `SUB_CMD` 补订阅，同时 PB5 状态灯三闪提示。补订阅期间（几次 AT 往返，
   通常 <1s）状态上报会短暂暂停。
8. **断线恢复有一分钟的"耐心"**：MQTT/WiFi 掉线后先交给 ESP-AT 自动重连，只有持续
   90s 不回来才升级成软恢复。所以短暂断线期间 PB5 会双闪、`home/state` 会停，
   这是设计行为，不是卡死。
8. **指令不重发 + 工具返回旧状态**：见第 1、4 条。
9. **`esp_mqtt_client_publish` 会短暂持锁**：发布在 `lifecycle_mutex_` 内执行，QoS 0
   正常是微秒级；只有 TCP 发送缓冲满时才会拖到网络超时。已用 `data_.connected` 前置
   挡掉断开时的无效发布。
10. **验证情况**：STM32 侧已在 Keil 里编译并链接通过 —— `MDK-ARM/smart_home/` 下
    各 `.o` 与 `smart_home.hex` 的时间戳都晚于全部源文件的最后一次修改。
    `docs/check_xiaozhi_link.py` 也已实跑通过（47 项检查、0 失败），覆盖
    小智工具载荷 → STM32 `home_cmd_apply()` 解析、两种 `+MQTTSUBRECV` 排版、
    `home/state` 两端字段对照。小智侧固件未在本机重新编译（本机没有 ESP-IDF），
    那部分的改动是按逐行静态审查 + 独立对抗式复核完成的。
